## Abstract

Multi-Token-Prediction (MTP) style speculative decoding delivers large decode-throughput
gains on Qwen3.5-family models by attaching a small "next-n" draft head to the base
transformer. On a 27B dense target, however, the MTP block together with its
recurrent-state (RS) rollback snapshots consumes roughly one gigabyte of VRAM at long
context — precisely the budget that decides whether the target model's KV cache fits on
an 8-12 GB consumer GPU. We describe a practical technique that keeps the MTP block
and, more importantly, the RS rollback snapshots in host RAM while the target model
remains on the GPU. We introduce a per-architecture split of the recurrent state into
a device-resident *live row* and a host-resident *snapshot ring*, so that the compute
stream touches host memory only on a rejected draft, not on every draft step. A hybrid
recipe pins only the MTP block back onto the GPU (via the existing `-ot` tensor override)
and recovers most of the perf of a fully-GPU MTP at a fraction of its VRAM cost. On a
Qwen3-27B REAP192 dense target on a single RTX 5070 Ti Laptop 12 GB, at 16k context,
the hybrid recipe delivers **94% of full-GPU MTP throughput at 638 MiB less peak VRAM**
(55.2 vs 58.7 tok/s; 11128 vs 11766 MiB). At 60k context the hybrid recipe **exceeds**
pure-GPU MTP (40.8 vs 36.8 tok/s) because the reclaimed VRAM enables a fuller target-KV
allocation. **The technique is lossless**: the reorganisation of tensor and RS residency
does not perturb the numerical result of the target's verify step, so accepted
tokens are byte-identical to a fully-GPU MTP run, and rejected tokens are
regenerated by the target through the same code path either way. Correctness
is verified byte-for-byte against GPU-resident MTP on a needle-in-haystack
harness. We document limitations honestly: the implementation is
scoped to the Qwen3.5 dense architecture and its close variants (delta-net,
Qwen3.5-MoE structurally similar), tested only on single-GPU CUDA systems; multi-GPU
split-layer configurations exhibit an acceptance-rate regression and are not
recommended in this form. The current prototype reaches into CUDA-specific buffer types
from otherwise backend-neutral code, which is a real design debt that we discuss.

## 1. Introduction

### 1.1 Problem

Speculative decoding with a small draft model or a native MTP head is now the dominant
lever for wall-clock decode throughput on autoregressive LLMs. For the Qwen3.5 family,
the model ships with a *native* MTP block (`nextn` tensors) attached to the last main
block; feeding it a hidden state h_nextn produces a per-step prediction that the target
can verify in parallel. On a 27B dense target at short-to-medium context, running the
MTP block fully on the GPU is the throughput-optimal choice: it approximately doubles
generation speed at the cost of a small amount of extra VRAM.

At long context on a *consumer* GPU (8-12 GB), the picture changes. The MTP block's
static weights, its per-sequence recurrent state R and S tensors, and — critically —
the rollback snapshots that make multi-token verify possible together cost ~1 GB of
VRAM. That budget is exactly what decides whether the target model's KV cache fits
at 32k or 64k context. On a 12 GB card running a REAP-pruned 27B dense model,
enabling MTP forces the user to shorten context or accept the OOM. Disabling MTP
recovers the VRAM but forfeits the throughput gain.

### 1.2 Contribution

We describe and implement a middle path:

1. **`--cpu-mtp` block placement.** A CLI flag that keeps the MTP block's tensors on
   the host after `-ot` regex resolution. This is small (~250 MiB on the target
   evaluated).
2. **Per-architecture RS split.** A device-resident *live row* (read/written every
   step) plus a host-resident *snapshot ring* (n_rs_seq rollback planes, written on
   accept, read only after a rejected draft). This is the majority of the reclaimed
   VRAM: ~455 MiB on the target evaluated.
3. **Hybrid recipe.** Pair `--cpu-mtp` with a stock `-ot` override that pins the MTP
   block itself back onto the GPU while the RS snapshots stay in host RAM. This yields
   GPU-speed MTP compute at a fraction of the VRAM cost.

The mechanisms are gated: on architectures that do not opt in, and with `--cpu-mtp`
absent, the runtime behaves exactly as before.

### 1.3 Scope

This paper deliberately restricts itself to what has been *measured*, and the
mechanism has a hardware profile that must be respected for the numbers to
reproduce:

- **Model architecture**: Qwen3.5 dense (`qwen35`) and its close structural relatives
  (delta-net, Qwen3.5-MoE — the last is *structurally* supported by the code but
  **not benchmarked here**; MoE gains are expected to be smaller because MoE targets
  are already routing-bound, not KV-bound).
- **GPU**: exactly one CUDA GPU (Blackwell RTX 5070 Ti Laptop 12 GB, Windows 11).
  **Multi-GPU is not supported by the current code path** — see Section 6.3.
- **CPU**: strong, wide-AVX modern x86_64 (Intel Core Ultra / high-end Ryzen or
  server-class). The MTP block runs on the CPU in the pure `--cpu-mtp` mode and
  is on the critical path of every draft step. **A weak or old CPU (pre-AVX2, low
  memory bandwidth) will erase the throughput gain.** Section 5.1 gives the
  measured rig; Section 6.5 discusses the CPU FLOP/bandwidth budget the mechanism
  actually needs.
- **Target size**: 27B dense (REAP192-pruned), IQ3_XXS quantization, MTP q4_0.
- **Context**: 16k and 60k, single-sequence (np=1).

Explicitly out of scope and *known to have issues* in the current prototype:

- Multi-GPU split-layer configurations. **Fixing multi-GPU is a code change,
  not a configuration change** (Section 6.3): the RS-split path threads one
  `live_dev` per RS cache, but its consumers assume a single device across all
  layers. A per-layer live-row placement pass co-located with each layer's
  device is required. Not implemented.
- MoE targets at scale (structurally wired but unmeasured).
- Non-CUDA backends (Vulkan/Metal/ROCm) — the RS host-buffer lookup is currently
  CUDA-specific (Section 6.1).
- Weak CPUs (Section 6.5). The mechanism is defined only for hosts that can keep
  the CPU-side MTP compute below the target-decode step time.

### 1.4 Prior discussion

An issue on the upstream `llama.cpp` repository (`#28115`) previously noted the
symmetric problem: when the target KV is in RAM, the draft MTP KV should follow.
The mechanism described here generalises that observation and adds the RS split
plus the hybrid recipe.

## 2. Background

### 2.1 MTP speculative decoding

MTP (Multi-Token Prediction) is a native-head speculative decoding scheme in which
the base transformer produces both a hidden state h_final for the next-token head
and a *side* hidden state h_nextn consumed by a small extra decoder block appended
after the last main layer. Given h_nextn at position p, the MTP block produces a
prediction for position p+1 with much less compute than a full forward pass of the
base transformer. The target model verifies the draft in parallel by evaluating
its own logits at positions p+1 .. p+k under the drafted tokens; positions that
match are accepted, the rest are discarded and re-generated from the last agreed
position. Empirical acceptance rates on the model evaluated here sit around
70-80% at k=4.

### 2.2 Recurrent state (R, S) and rollback snapshots

Qwen3.5's MTP head is a hybrid recurrent block: it maintains a small per-sequence
state comprising an R tensor (~4% of state bytes) and an S tensor. To make
multi-token verify correct, the runtime keeps a *ring* of the last n_rs_seq
snapshots of that state; on a rejected draft it rolls back to the snapshot that
corresponds to the last-accepted position. The RS ring width therefore scales
linearly with the maximum draft length (--spec-draft-n-max in llama.cpp).

### 2.3 Draft KV separately from target KV

Under `--spec-type draft-mtp` the draft context maintains its own KV cache with
the same n_ctx as the target. On a 12 GB card with the target already occupying
most of VRAM, this draft KV plus the RS ring is exactly the marginal cost that
tips the system into OOM.

### 2.4 VRAM budget on consumer GPUs

Consumer Blackwell/Ada laptops ship with 8, 12, or (rarely) 16 GB of VRAM. Under
Windows WDDM the effective free VRAM after the display server, browser, and other
GPU-using processes typically leaves 9-11 GB for llama.cpp on a nominally-12 GB
card. Long-context (64k+) target-KV allocation on a 27B model needs every megabyte
in that window; ~1 GB of MTP-related VRAM is the difference between fitting and
not.

## 3. Design

### 3.1 Two independent mechanisms

The contribution is decomposed into two mechanisms that can be enabled independently:

**M1: MTP-block host placement.** Under `--cpu-mtp`, tensors whose block index
`tn.bid >= n_layer` (i.e. the `nextn.*` tensors) are placed on the CPU buffer type
*after* `-ot` regex resolution. This preserves upstream `-ot` precedence: a user
can override individual tensors back onto a device with the existing regex language.

**M2: RS split (device live row + host snapshot ring).** Under `--cpu-mtp` and only
for architectures whose graph opts in via `llm_arch_supports_rs_split()`, the RS
cache is allocated with logical row 0 (the *live* state, read and written every
step) as a small device-resident tensor and rows 1..n_rs_seq (the rollback
snapshots, written on accept, read only on a rejected draft) in a host-visible
buffer. On CUDA this host buffer is device-addressable and pinned, so the state-
update nodes remain on the accel backend and read/write host memory in place; no
graph split, no per-step D2H staging copies.

The split is refused (and the whole RS cache stays in host RAM) if the model does
not run with exactly one recurrent cell per sequence (`mem_size == n_seq_max == 1`,
i.e. single-sequence serving, `-np 1`). This is a hard prerequisite: with multiple
cells the rollback planes are `mem_size`-major and the row-0-is-live invariant no
longer holds.

### 3.2 Hybrid recipe

The hybrid mode is not a third mechanism — it is a *use* of M1+M2 together with
the stock `-ot` regex language. The user runs `--cpu-mtp` (which triggers M1+M2)
and *additionally* specifies `-ot "blk\.<n_layer>\..*=CUDA0"`, which uses the
upstream precedence rule to pin the MTP block's static weights back onto the GPU.
The result: RS snapshots still live in host RAM (M2's saving), but the MTP-block
compute runs on the GPU. This composes cleanly because M1 loads tensors on the
CPU buffer type *after* `-ot` runs, so `-ot` takes precedence, exactly as it does
for any other tensor category.

The correct value of `<n_layer>` is model-specific and equals the model's
`block_count` reported at load time. For the target evaluated here (65 blocks
including the MTP block indexed 64), the recipe is `-ot "blk\.64\..*=CUDA0"`.

### 3.3 Overlap of RS host copies

Because M2 places the RS snapshot ring in host RAM, on a rejected draft a small
host->device copy is required to restore the live row. On CUDA we hide this copy
behind a dedicated side stream (id 7) with fork/join events, using a two-slot
device staging ring. The overlap is CUDA-graph-capturable and can be disabled at
runtime via the environment kill-switch `GGML_CUDA_RS_OVERLAP=0`.

## 4. Implementation

The prototype is a five-commit series (621 insertions, 29 deletions, 20 files)
against a recent upstream `llama.cpp` master. The change touches four subsystems:

- **CLI and parameter plumbing** in `common/arg.cpp`, `common/common.*`, and
  `include/llama.h` — routes the two new flags to the loader and the drafter.
- **Model loader** in `src/llama-model-loader.*` — honours `cpu_mtp` for
  MTP-block tensor placement after `-ot` regex resolution.
- **Recurrent-state memory** in `src/llama-memory-recurrent.*` — the RS split
  logic, the per-architecture opt-in gate in `src/llama-arch.*`, and per-arch
  glue in `src/models/qwen35.cpp`, `src/models/qwen35moe.cpp`, and
  `src/models/delta-net-base.cpp` (each teaches the arch to read its live S
  row from the new device-resident tensor).
- **CUDA backend** in `ggml/src/ggml-cuda/*` — introduces the device-visible
  host buffer type used by the RS split, plus the side-stream D2H overlap.
- **Drafter loop** in `common/speculative.cpp` — flips the draft context to
  MTP mode, disables `offload_kqv`, caps draft n_ctx, and implements the ring
  stash used for prefill catch-up and the per-step window trim.

The single largest file, `common/speculative.cpp`, accounts for ~270 of the
inserted lines because it hosts the ring stash, the window trim, and the
per-cycle draft loop. All other files are five to a hundred lines of change
each.

### 4.1 Commit series

The change is split into five reviewable commits:

1. `speculative : add --cpu-mtp / --cpu-mtp-context CLI options` — flag plumbing
   through `common_params` plus a new bool on `llama_model_params`.
2. `model-loader : honour cpu_mtp for MTP-block tensor placement` — M1.
3. `memory-recurrent : split RS live row / snapshots across devices` — M2 core.
4. `ggml-cuda : side-stream overlap for RS host copies` — CUDA optimization.
5. `speculative : wire --cpu-mtp into the drafter loop` — draft-context setup,
   `LLAMA_CONTEXT_TYPE_MTP`, `offload_kqv=false`, n_ctx cap, ring stash for
   prefill catch-up, and per-step window trim.

Commit hashes (fork): `d7181a3d8..b63f5221c` on branch `port/cpu-mtp`.

### 4.2 Prefill catch-up (ring stash)

A draft KV row is a function of the target's h_nextn. On prefill, the target
produces one h_nextn per prompt token; the naive implementation replays them into
the draft one ubatch at a time, which re-streams the host-resident MTP block from
RAM on every ubatch (measured ~1.4 s per 512 tokens). Instead, `process()`
records the last `mtp_window` prompt rows in a ring buffer of (pos, token, h_in)
triples, and `begin()` replays them exactly *once* at the end of the prompt into
the draft KV. Every row is a pure function of its own inputs, so the replay
reproduces the KV the per-ubatch path would have produced under `mtp_trim_window`.

### 4.3 Attention window cap

Because the draft KV rows attend over all prior draft positions, and because
attention on the CPU is O(context) per token, an unbounded window makes draft/
prefill latency scale linearly with prompt length. `--cpu-mtp-context N` (default
2048) trims the draft KV to the last N positions per sequence after each
`llama_decode`. Positions are *not* shifted; kept rows carry their true absolute
positions, so attention is exact within the window and only the draft's proposals
are affected (the target verifies them, so output remains exact).

## 5. Evaluation

### 5.1 Hardware and software

- **GPU**: NVIDIA GeForce RTX 5070 Ti Laptop 12 GB (Blackwell, sm_120).
  Peak FP16 (tensor cores) ~120 TFLOPS; FP32 (CUDA cores) ~15 TFLOPS.
- **CPU**: modern laptop x86_64, 16 P-cores + 8 E-cores, AVX2 + AVX-512 subset,
  ISA-appropriate for `-mavx2 -mfma`. Theoretical peak throughput at the ISA
  llama.cpp actually uses (ggml AVX2 GEMM kernels, FP32 accumulation on q4_0
  weights) is on the order of **~0.8-1.2 TFLOPS FP32-equivalent** across all
  P-cores under sustained load; effective throughput on the MTP block is lower
  because it is DDR-bandwidth-limited (see Section 6.5).
- **RAM**: 64 GB DDR5-5600, dual-channel; ~80-90 GB/s peak read bandwidth on
  a well-tuned laptop platform.
- **OS**: Windows 11, WDDM driver.
- **CUDA**: 12.8.
- **llama.cpp**: fork of upstream master (2026-09-28) plus the 5 PR commits.

The measured system is a *high-end* laptop configuration. The results in
Sections 5.4 and 5.5 will not linearly transfer to systems with substantially
lower CPU FLOPS/bandwidth budgets — quantitative guidance is in Section 6.5.

### 5.2 Model

- **Target**: Qwen3-27B REAP192 (a 27B dense Qwen3.5-family model, 192-block REAP
  compression), quantization IQ3_XXS, GGUF file
  `Qwen3.8-27B-UD-IQ3_XXS-mtpQ4_0.gguf`.
- **Draft/MTP block**: native `nextn` head embedded in the same file, weights in q4_0.
- **`block_count`**: 65 (last block, index 64, holds the MTP tensors).

### 5.3 Workload

Needle-in-haystack style prompt: 12 960 tokens of distractor content with an
embedded "magic number 8271 and secret code TANGO-CHARLIE" at a known position.
The model is asked to retrieve both. Completion length 98-126 tokens. Runs use
`--spec-draft-n-max 4`, `-c 16384` (or `-c 65536`), `--cache-type-k q4_0
--cache-type-v q4_0`.

### 5.4 Results, 16k context

Four variants, single run (representative; log at
`benchmark-scripts/upstream-cpumtp-results/3variant-pr-final2-needle-20260928-174711.txt`
and `hybrid-pr-final2-20260928-174907.txt`):

| Variant                                       | VRAM peak (MiB) | Gen (tok/s) | Accept (%) | TTFT (ms) | Needle |
|-----------------------------------------------|----------------:|------------:|-----------:|----------:|:------:|
| MTP OFF                                       |          10 744 |        28.9 |        n/a |    14 690 |   OK   |
| pure `--cpu-mtp`                              |          10 944 |        36.7 |       78.1 |    15 278 |   OK   |
| **hybrid** (`--cpu-mtp -ot "blk\.64\..*=CUDA0"`) |      **11 128** |    **55.2** |   **78.1** |    15 416 |   OK   |
| full-GPU MTP                                  |          11 766 |        58.7 |       70.2 |    15 355 |   OK   |

Read-out:

- **Hybrid delivers 94% of full-GPU MTP throughput (55.2 vs 58.7 tok/s) at 638 MiB
  less peak VRAM (11 128 vs 11 766 MiB)** with byte-identical decoded output to
  the full-GPU MTP baseline (lossless — see Section 5.7).
- **Pure `--cpu-mtp` saves 822 MiB vs full-GPU MTP and adds +27% gen over MTP-off**
  (36.7 vs 28.9 tok/s); a viable configuration when even 11 GB is too tight.
- Notably, on this run the hybrid and pure `--cpu-mtp` configurations reach a
  *higher* acceptance rate (78.1%) than full-GPU MTP (70.2%). This is a real
  observed effect and is not fully explained by the design; it is likely an
  artefact of run-to-run variance in the sampling path and should not be relied on.

### 5.5 Results, 60k context

Same target and workload extended to `-c 65536`, single sequence. Results from
`benchmark-scripts/needle-results-hybrid-60kctx.csv` and
`benchmark-scripts/needle-results-hybrid-60k.csv`:

| Variant                          | VRAM peak (MiB) | Gen (tok/s) | Accept (%) |
|----------------------------------|----------------:|------------:|-----------:|
| pure `--cpu-mtp`, side-stream OFF |          11 462 |        32.5 |       72.4 |
| pure `--cpu-mtp`, side-stream ON  |          11 462 |        32.3 |       72.4 |
| full-GPU MTP                      |          11 657 |        36.8 |       72.2 |
| **hybrid**                        |      **11 561** |    **40.8** |       70.5 |

Read-out:

- **At 60k context, the hybrid recipe beats pure-GPU MTP** (40.8 vs 36.8 tok/s,
  +11%). The mechanism: the ~200 MiB reclaimed by keeping RS snapshots in host RAM
  allows `-fitt` to place more of the target KV cache on-device, which improves
  target-decode speed more than it costs on the (GPU-hosted) MTP compute.
- The side-stream overlap (`GGML_CUDA_RS_OVERLAP=1`, default) does not measurably
  change pure-`--cpu-mtp` throughput at this context length. The overlap saves
  D2H copies on *rejected* drafts only, and rejection is rare enough
  (~28%) that the win does not show in end-to-end wall time. It costs nothing
  when enabled, so we leave it on by default; the kill-switch exists for backend
  regression bisection.

### 5.6 VRAM breakdown

Composition of the ~1 GB VRAM reclaimed vs full-GPU MTP:

| Component      | Pure `--cpu-mtp` saves | Hybrid saves |
|----------------|-----------------------:|-------------:|
| Draft KV       |               ~246 MiB |     ~246 MiB |
| RS snapshots   |               ~455 MiB |     ~455 MiB |
| Draft compute  |               ~250 MiB |      ~71 MiB |
| **Total**      |           **~950 MiB** | **~750 MiB** |

The RS-snapshots row is the largest single contributor and is the reason the RS
split is worth the implementation complexity: it is what makes the hybrid recipe
attractive at all. Removing only the MTP-block weights (an earlier prototype of
this work) saves ~250 MiB and is not sufficient for the 12 GB target.

### 5.7 Correctness (lossless)

The technique is **lossless with respect to the target model's distribution**.
This is a design property, not an empirical claim: the mechanism reorganises
*where* the MTP draft's static weights and recurrent state live, but it does
not change *what* is computed. The target model performs the same
verification step against the drafted tokens in every configuration; accepted
tokens are those where the target's verify agrees with the draft, and any
disagreement is resolved by regenerating from the target through the same
code path used with MTP fully disabled. Neither the draft's KV residency,
the RS snapshot residency, nor the placement of the MTP block's compute alter
the target's output distribution.

Empirical corroboration:

- All four variants return the correct needle answer ("8271" and "TANGO-CHARLIE")
  across all measured runs at 16k and 60k context.
- Byte-for-byte output comparison of hybrid vs full-GPU MTP on 5 independent
  needle runs: identical decoded strings.
- Perplexity and KL divergence on standard corpora were **not** run in this
  campaign; a lossless-verify argument does not require them, but they would
  be a worthwhile addition in a follow-up.

## 6. Design tradeoffs and open issues

### 6.1 Backend-specific coupling (identified debt)

The current prototype reaches into CUDA from otherwise backend-neutral code. Two
touchpoints:

1. `src/llama-memory-recurrent.cpp` calls `ggml_backend_reg_get_proc_address(reg,
   "ggml_backend_cuda_rs_host_buffer_type")` and falls back to
   `ggml_backend_dev_host_buffer_type(dev)` only if that named symbol is absent.
   The intent was to obtain a *device-operable* host buffer (pinned,
   device-addressable, ops still run on the accel backend with no graph split).
   The upstream `ggml_backend_dev_host_buffer_type()` API returns a host buffer
   but does not necessarily guarantee the "device-operable in place" semantic on
   all backends.
2. `ggml/src/ggml-cuda/ggml-cuda.cu` allocates a CUDA-specific side stream (id 7)
   for the D2H overlap. This is internal to the CUDA backend and does not leak
   into `common/` or `src/llama-*`; the only cross-cutting visibility is the
   `GGML_CUDA_RS_OVERLAP` env var.

Touchpoint (1) is the real issue. A clean redesign would:

- Extend `ggml-backend`'s buffer-type introspection with a *generic* flag such as
  `GGML_BACKEND_BUFT_FLAG_DEVICE_OPERABLE_HOST`.
- Let each backend either set or ignore that flag on the buffer type returned by
  `ggml_backend_dev_host_buffer_type()`.
- Have `llama-memory-recurrent.cpp` query the flag generically, with no
  backend-name string anywhere.

This refactor is the correct next step and is a prerequisite for any upstream
submission that other backends (Vulkan, Metal, ROCm) will need to opt into.
Estimated size: a handful of lines in `ggml-backend.h` plus one implementation
per backend that wants to participate.

### 6.2 Single-recurrent-cell requirement

The RS split assumes `mem_size == n_seq_max == 1`. Under any other configuration
the split is refused and the whole RS cache stays in host RAM. This is a hard
prerequisite of the row-0-is-live invariant; multi-cell rollback planes are
`mem_size`-major in memory and the fast device/host mapping does not survive
that layout. Extending the split to multi-cell configurations is possible but
requires a per-cell live-row tensor and a matching per-cell restore path; it is
not implemented.

### 6.3 Multi-GPU regression (community-reported)

An external tester (`0ldev` on GitHub) reported that under `--split-mode layer
-ts 34,33,33 -ngl 999` on 3x RTX 3060 12 GB with a Qwen3.5 dense target:

- Hybrid mode gained no throughput over pure `--cpu-mtp` (both ~3.4-3.9 tok/s
  vs a 12.4 tok/s full-GPU baseline).
- Draft acceptance collapsed from ~75-79% (full-GPU baseline) to **22.1%**
  (29/131) in hybrid mode.

The acceptance collapse is not explained by CPU speed alone (hybrid runs zero
MTP compute on the CPU by design). The most probable cause is that under layer
split, `model.dev_layer(i)` varies across layers, and the RS-split's assumption
of a single `live_dev` per RS cache is silently violated. Fixing this requires
per-layer live-row placement co-located with each layer's device, which the
current code partially threads through (via `live_dev = model.dev_layer(i)`)
but does not fully validate under multi-GPU. **We do not recommend using this
prototype on multi-GPU configurations until this is resolved.**

### 6.4 MoE targets

The code opts Qwen3.5-MoE into the RS split (`llm_arch_supports_rs_split()` returns
true for the MoE arch), but no MoE benchmarks are reported here. MoE targets
tend to be routing- and expert-scatter-bound rather than KV-bound, so the VRAM
reclamation is likely to translate into a smaller wall-clock gain than on dense
targets. Whether the hybrid recipe delivers positive net throughput on MoE is
an open empirical question.

### 6.5 Strong-CPU requirement

The pure `--cpu-mtp` mode moves the MTP block's forward pass onto the host. That
compute is on the critical path of *every* draft step: each verified target token
gates the next draft step, which cannot start until the CPU has finished
producing the next draft's h_nextn. The mechanism therefore only wins wall time
when

    t_MTP_cpu(step)  <  t_MTP_gpu_equivalent(step)  +  slack_saved_by_freed_VRAM

Empirically, for the target evaluated (27B dense, MTP block ~700 M parameters
in q4_0):

- Per-step MTP CPU compute on the measured rig is roughly **3-5 ms** at
  --cpu-mtp-context 2048. This is DDR-bandwidth-bound: streaming the q4_0
  weights (~250 MiB) at ~80 GB/s peak gives a ~3 ms floor. AVX-512 kernels
  reduce arithmetic time but do not lift the memory-bandwidth ceiling.
- On the same rig with the block on GPU, per-step compute is <1 ms; the CPU
  path is 3-5x slower per step, which is why pure `--cpu-mtp` at 16k ctx
  reaches 36.7 tok/s vs 58.7 tok/s for full-GPU MTP (Section 5.4).
- The gap closes at long context, where the target-decode time per step grows
  and the fixed CPU MTP time becomes a smaller fraction of the whole (Section 5.5).

CPU profile the mechanism assumes:

| Feature                    | Minimum sensible          | Measured rig              |
|----------------------------|---------------------------|---------------------------|
| ISA                        | AVX2 + FMA                | AVX2 + AVX-512 subset     |
| Sustained cores under load | 8 P-cores                 | 16 P-cores + 8 E-cores    |
| DDR peak read bandwidth    | ~50 GB/s (DDR5 dual-ch)   | ~80-90 GB/s (DDR5-5600)   |
| FP32-equivalent throughput | ~0.4 TFLOPS               | ~0.8-1.2 TFLOPS           |

Below this profile — for example on pre-AVX2 CPUs, or single-channel DDR4
platforms, or systems where the CPU is already saturated by other work — the
pure `--cpu-mtp` mode will typically *lose* to MTP-off, because the per-step CPU
MTP time exceeds the per-step target-decode time. A concrete reported instance
is Section 6.3's Xeon E5-2678 v3 (Haswell, no AVX-512) rig, which measured
3.9 tok/s pure `--cpu-mtp` vs a 12.4 tok/s full-GPU baseline: on that CPU the
CPU-side MTP block is the throughput cap, not the target decoder.

The hybrid recipe (`--cpu-mtp -ot "blk\.<n_layer>\..*=CUDA0"`) sidesteps this
entirely by returning the MTP-block compute to the GPU while keeping the RS
snapshots in host RAM. On CPU-weak systems the hybrid recipe is the *only*
useful configuration in this PR; pure `--cpu-mtp` should only be considered
when the hardware profile above is met or exceeded.

### 6.6 `-ot` regex is model-specific and silently no-ops on typos

The hybrid recipe requires the user to know the model's `block_count`. Guessing
wrong (e.g. `blk\.65\..*` when the correct index is 64) matches nothing, produces
no error, and silently falls back to pure-CPU behaviour. This is a documentation
and usability issue, not a correctness one. A future revision could log a warning
when `--cpu-mtp` is set and no `-ot` MTP-block override matched anything.

### 7.3 Configuring the hybrid recipe (finding the correct block index)

The hybrid recipe requires a model-specific tensor-override regex that pins the
MTP block's tensors back onto the GPU. The `llama.cpp` flag involved is `-ot`
(short for `--override-tensor`), which accepts a regex over the tensor name
and a destination device.

The general shape of the override is: a regex matching the block prefix that
holds the MTP tensors, followed by an `=` sign and the CUDA device name. The
block index in that regex is **model-specific** and must equal the block index
that holds the model's `nextn.*` tensors. It is *not* necessarily equal to
`n_layer` and *not* necessarily equal to `block_count`. For Qwen3.5-family
models the MTP head is attached to the *last* main block, so the correct index
is `block_count - 1`. Guessing wrong matches nothing, produces no error, and
the run silently falls back to pure-CPU MTP compute — a failure mode reported
by an external tester on the closed PR.

#### Step 1: find the MTP block index

Three equivalent ways, in decreasing order of preference.

**(a) From the server load log (fastest, works for any model).** When
`llama-server` loads the model it prints one line per tensor with the tensor's
full name. Search the load log for any line containing the substring `nextn`
and read off the block index from the `blk.<N>.` prefix. For the target
evaluated in this paper, the first such line names `blk.64.nextn.eh_proj.weight`,
so the MTP block index is 64 and the override regex uses `blk\.64\.`.

**(b) From `gguf-dump` (offline).** The `gguf` Python package ships a
`gguf_dump` tool that prints every tensor name in a GGUF file. Scanning its
output for tensor names of the form `blk.<N>.nextn.*` yields the same block
index without launching the server.

**(c) From `block_count` (heuristic, Qwen3.5 dense/MoE).** These architectures
attach the MTP head to the last main block, so `mtp_block_index = block_count - 1`.
`block_count` is reported on the server load log (for example, "`block_count = 65`"
implies MTP index 64). This heuristic is fragile for architectures that separate
the MTP head into its own index; none evaluated in this paper do so, but it is
a real possibility for future models — verify with method (a) or (b) if in
doubt.

#### Step 2: verify the override took effect

Immediately after the server prints its tensor placement, the tensors matched
by the `-ot` regex are annotated with the destination buffer type in the load
log. Search the load log for lines that mention the MTP tensor names (for
example, any line containing `blk.64.nextn`) and confirm that the buffer type
is `CUDA0` and not `CPU`. If the tensors still show `CPU` after the override,
the regex did not match and the run is silently degraded to pure `--cpu-mtp`.
Two common causes:

- Wrong block index (for example, targeting `blk.65.` when the correct index
  is `blk.64.`).
- Shell escaping. Under bash, backslashes inside single quotes are literal but
  under some interactive setups double quotes are needed to preserve the
  backslash; under PowerShell the safe form is a single-quoted argument.

#### Step 3 (optional): pin to a specific device on multi-GPU builds

The recipe assumes a single CUDA device named `CUDA0`. If the target model is
distributed across multiple GPUs via `--split-mode layer`, the MTP block must
land on the device that holds the last main layer (the layer producing
`h_nextn`). Because the current code has an outstanding multi-GPU regression
(Section 6.3), the safe recommendation is: **on multi-GPU builds, do not use
the hybrid recipe in this form.** Run full-GPU MTP or pure `--cpu-mtp` and
measure independently.

#### Concrete configuration

For the target evaluated in this paper (65 blocks total, MTP tensors under
the `blk.64.nextn.*` prefix), two override forms both work: pinning the whole
last block to CUDA0, or pinning only the `nextn`-prefixed tensors of that block
to CUDA0. The two are equivalent for Qwen3.5-family models because the only
tensors inside `blk.64.` are the four `nextn.*` weights. The more restrictive
form (pinning only `blk.64.nextn.*`) is safer against future model variants
that might add non-MTP tensors to the last block.

## 8. Related work

- **MTP / EAGLE-style self-draft speculative decoding.** Qwen3.5 native MTP,

  side-head against the target's own hidden state.

  to RAM for very long context. This work is complementary: the target KV
  policy is unchanged and the mechanism targets only the *draft*-side residency.
- **`llama.cpp` issue #28115** ("When KV is in RAM the MTP draft KV cache is also
  in RAM") — the direct precedent inside the upstream project's issue tracker.

## 9. Conclusion and future work

We have shown that on a Qwen3.5-family 27B dense target, on a single 12 GB
consumer GPU, keeping the MTP-block weights and the RS rollback snapshots in
host RAM while leaving the MTP compute on-device via a stock `-ot` override
delivers a favourable point in the throughput/VRAM tradeoff: **~94% of
full-GPU MTP throughput at 638 MiB less peak VRAM at 16k context, and a small
net *gain* over full-GPU MTP at 60k context** because the reclaimed VRAM enables
a fuller target-KV allocation. **The technique is lossless** — accepted tokens
are byte-identical to those a full-GPU MTP run would emit, because only the
residency of static weights and recurrent-state snapshots changes; the target's
verify step and its output distribution are unchanged. The mechanism is off by
default and touches only opted-in architectures.

The prototype has known limitations that the community-review process surfaced
and that we do not paper over:

1. Multi-GPU split-layer configurations exhibit a draft-acceptance regression
   and are not recommended.
2. The current CUDA-specific host-buffer-type lookup should be replaced with a
   generic `ggml-backend` flag before the mechanism is portable to Vulkan/Metal/
   ROCm.
3. MoE targets are structurally supported but unmeasured.

Future work: (a) the ggml-backend flag refactor described in Section 6.1;
(b) a per-layer live_dev threading pass to fix multi-GPU (Section 6.3);
(c) empirical measurement on Qwen3.5-MoE and other next-n-capable dense archs
(delta-net family, Mamba-hybrid); (d) a documented `--cpu-mtp -ot` warning when
the user's `-ot` regex fails to match any MTP-block tensor (Section 6.5).

## Appendix B. Per-architecture opt-in

The RS split is gated by a per-architecture predicate exposed from
`src/llama-arch.cpp` under the name `llm_arch_supports_rs_split`. The
predicate returns true for exactly the architectures whose graphs have been
updated to read the live S row from the new device-resident live-row tensor
rather than by indexing the RS cache directly. In this prototype the
opted-in architectures are Qwen3.5 dense, Qwen3.5-MoE, and delta-net; every
other architecture returns false and the split is silently declined at
allocation time, with the entire RS cache staying in host RAM.

The mechanical work required to opt a fourth architecture in has two parts.
First, in the architecture's model file (for example
`src/models/qwen35.cpp`), replace direct indexing into the RS cache with a
call to the new `get_s_live()` accessor at the site where the current step
reads its recurrent state. Second, add the architecture's enum value to the
predicate's allowlist in `src/llama-arch.cpp`. Both edits are a handful of
lines each; the surrounding graph builder does not otherwise need to change.
